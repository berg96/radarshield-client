# Версионирование RadarShield

Один источник правды — поле `version` в `pubspec.yaml`:

```
version: <major>.<minor>.<patch>+<build>
         └──── versionName ────┘ └ versionCode
```

## Что значит каждое число (semantic versioning)

| Часть | Когда поднимать | Пример |
|-------|-----------------|--------|
| **major** | Несовместимые изменения (сменился протокол подписки, миграция данных, ломающий редизайн) | `1.0.0` → `2.0.0` |
| **minor** | Новая фича без поломки совместимости (новый экран, split-tunnel, выбор сервера) | `0.1.0` → `0.2.0` |
| **patch** | Багфикс/мелкая правка | `0.1.0` → `0.1.1` |
| **build** (`+N`) | На КАЖДОЙ публикуемой сборке +1. Идёт в Android `versionCode` | `+1` → `+2` |

`versionName` (`0.1.0`) видит пользователь. `versionCode` (`1`) — внутреннее число
Android: **обязано только расти**, иначе обновление поверх отклоняется как «откат».

## Правила

1. **Каждая сборка, которую отдаём в TG/наружу** → подними `build` (`+N`) минимум на 1.
   Без этого Android не даст обновиться поверх (одинаковый versionCode).
2. Багфикс → `patch`. Фича → `minor`. Поломка совместимости → `major`.
3. Пока собираем собственный UI и нет публичного релиза — остаёмся в `0.x`
   (pre-1.0). Первый «полноценный» релиз пользователям = `1.0.0`.
4. **Точечно, не пачками.** Не прыгаем `v1 → v2`: правильно `0.1.0 → 0.1.1 → 0.2.0`.

## Примеры

```
0.1.0+1   первый собственный UI-shell (полноэкранный главный + онбординг)
0.1.1+2   фикс: убран баннер FLClash / мелкие правки экрана
0.2.0+3   фича: свой экран выбора сервера
0.2.1+4   фикс пинга в выборе сервера
1.0.0+10  первый публичный релиз
```

## Подпись и обновления

Обновление поверх работает только если **(а)** `versionCode` вырос **и**
**(б)** APK подписан тем же сертификатом. Поэтому в репозитории лежит стабильный
debug-keystore (`android/app/radarshield-debug.keystore`), которым подписываются
все CI-сборки — см. `android/app/build.gradle.kts`. Менять его нельзя: смена
ключа = пользователю придётся удалить и поставить заново.
